## 一、背景与定位

**定位**：学习用、辅助用的桌面翻译工具。解决"屏幕上有一小片英文，看不懂，但专门去查太麻烦"这个高频小痛点。

目标场景：IDE 的函数提示与报错、视频字幕、PPT 副标题、网页上一段英文说明。

立项动机是三条具体的不满（也就是本项目的全部差异化价值）：

1. 每次都要重新框选，重复操作多
2. 弹窗遮挡原内容
3. 界面太繁琐，视觉引导不清晰；边框不支持深色模式，某些场景下突兀

**明确不做**：全能翻译工具。不做剪贴板监听、不做划词翻译、不做 AI 生图/总结/问答、不打包本地大模型、不自训模型。

## 二、平台与实现方式

| 项 | 决定 | 说明 |
| --- | --- | --- |
| 运行平台 | **Windows 优先** | 其他平台不在 V1 范围 |
| 技术栈 | **Tauri v2 + Rust + 原生 TS** | M0 已验证透明/穿透/置顶/抓屏全部可行 |
| 发行形态 | 单 exe + 零服务器 | 无账号体系、无后端、无中转 |

**放弃的方案**：

- **浏览器插件**——只能在浏览器里跑，且浏览器自带翻译；无法覆盖 IDE 与其他软件。
- **Fork Pot**——GPL-3.0 传染性（衍生项目必须同样 GPL-3.0），且需读懂一个成熟的大型 Rust + React 代码库，成本高于从零写。
- **C# WPF 兜底**——只在 Tauri 透明方案失败时作为后备，M0 已验证不需要。

## 三、核心交互

### 3.1 三种形态

- **A 框选截图**：快捷键唤起 → 全屏暗化 → 拖框 → 就地显示译文
- **B 常驻玻璃窗**：半透明、置顶窗口钉在屏幕上，底下内容透出，译文叠在上面
- **C 悬挂隐形**：边框与工具条全透明、窗口点击穿透，但**译文层保持可见**；再按一次快捷键恢复

### 3.2 玻璃窗记住矩形（针对"每次重新框选"）

玻璃窗一旦建立，就记住自己的屏幕矩形。之后按重译快捷键，只对这块矩形重新抓屏 + 识别 + 翻译，不需要重新框选。这是相对同类工具最直接的省时点。

⚠️ **实测补充（M0/T3）**：窗口跨显示器移动时，物理尺寸会随目标屏 DPI 改变（逻辑尺寸不变）。所以这个矩形必须**每次抓屏前现取**（`GetWindowRect` 或 `outer_position` + `outer_size`），不能在建窗时缓存一次就用到底。

### 3.3 不冻结屏幕

玻璃窗是真透明窗口，底下的视频继续播、游戏继续跑，不存在画面定格。这与全屏遮罩式截图有根本区别——后者在视频/动画场景下会让人明显感觉画面卡住。

⚠️ **待补的设计缺口**：「不冻结」的另一面是**区域内容可能在抓屏瞬间变了**（视频切镜头、页面滚动、光标闪烁）。M1 之后需要加失效检测：若重译结果与上一次差异过大而无用户操作，或对上屏幕当前内容与上次抓屏的哈希不匹配，则提示"这块内容已变化"。暂记为 M3 事项。

### 3.4 状态机

```
[无] --Alt+Q--> [框选中] --松手--> [识别/翻译中] --> [覆盖显示]
[覆盖显示] --Alt+W--> [识别/翻译中] --> [覆盖显示]
[覆盖显示] --Alt+E--> [隐形悬挂]
[隐形悬挂] --Alt+E--> [覆盖显示]
[任意态] --Alt+R--> [无]
[任意态] --Esc---> 取消当前操作，回到上一稳定态
```

### 3.5 快捷键（默认值，全部可改）

| 键 | 动作 |
| --- | --- |
| `Alt+Q` | 新建玻璃窗（全屏暗化 → 拖框） |
| `Alt+W` | 对当前玻璃窗重截 + 重译，无需重新框选 |
| `Alt+E` | 隐形 / 显形切换 |
| `Alt+R` | 关闭当前玻璃窗 |
| `Esc` | 取消当前操作 |

支持多个玻璃窗并存；快捷键作用于"当前聚焦"的玻璃窗。

## 四、译文原位覆盖（核心难点）

四步方案：

1. **拿行级坐标**：OCR 返回每行/每词的 bounding rect（`OcrLine.BoundingRect`）
2. **段落聚合**：按行间距阈值把 OCR 行合并成段。**必须按段翻译，不能按行翻译**——逐行送翻会丢上下文，质量明显下降
3. **抹除原文**：在该段所有行框上画不透明色块，颜色取自行框**外扩 2px 的边缘像素众数色**
4. **回填译文**：译文渲染进该段第一行位置，字号按可用高宽自适应缩放；该段其余行框保持抹除

**降级策略**：若背景色方差过大（渐变、图片、代码高亮），自动降级为「半透明深色底 + 白字」，牺牲无缝感换可读性。V1 不试图解决复杂背景。

**译文过长的处理**：字号有下限；低于下限仍放不下时折行；再放不下则提示"区域太小，建议重新框选"。

### 4.1 坐标体系（M0 实测结论）

这是整个项目最容易埋 bug 的地方，规则只有一条：**Rust/Win32 侧全部用物理像素，CSS 侧全部用逻辑像素，跨界只在一个地方换算**。

| 位置 | 单位 | 来源 |
| --- | --- | --- |
| `window.outer_position()` / `outer_size()` | **物理像素** | Tauri v2（实测，与 `GetWindowRect` 逐像素一致） |
| `Monitor.position()` / `.size()` | **物理像素** | 同上 |
| `window.scale_factor()` | 倍率（物理 / 逻辑） | 逐窗口，跨屏会变 |
| DOM 事件（`clientX`、`getBoundingClientRect()`） | 逻辑像素 | 浏览器 |

结论：**不要对 Tauri 返回的坐标再乘一次 `scale_factor`**。需要把 DOM 坐标转成物理像素时，才乘 `devicePixelRatio`。

### 4.2 抹除块的自适应与主题的关系

抹除块的底色**不写死**，来自截图采样，因此天然贴合背景；需要显式适配深色的是工具条与设置窗（三档主题，默认跟随系统）。这两件事不要混为一谈。

## 五、界面硬约束

以下五条是**硬性约束，不是后续优化项**：

1. **玻璃窗默认没有任何 UI 元素**：无标题栏、无按钮、无边框、无 logo，屏幕上只有译文本身。所有操作走快捷键。
2. **工具条只在鼠标悬停时浮现**：四个无文字图标（重译 / 复制 / 关闭 / 设置），移开立即消失。设置窗是独立窗口，平时完全不存在。
3. **覆盖层配色跟着目标区域走**，工具条与设置窗提供浅色 / 深色 / 跟随系统三档。
4. **首次启动三步引导，不做教程**：选引擎 → 粘贴 AccessKey → 立刻试翻一张，全程不超过一分钟。
5. **专注模式**：一键关闭历史记录写入、悬停工具条、所有过渡动画、离线 OCR 后台预加载，只保留"快捷键 → 翻译 → 覆盖显示"。默认关闭。

### 5.1 穿透与工具条的实测约束（M0/T2）

- 整窗穿透用 Tauri 的 `set_ignore_cursor_events(true)`，**不需要**手写 `WS_EX_TRANSPARENT` / `WS_EX_LAYERED`。
- 但窗口处于穿透态时收不到任何鼠标消息，`mouseenter` / `mousemove` 都不会触发。**所以"悬停浮现工具条"只能靠 Rust 侧轮询 `GetCursorPos`**，判断光标是否落在窗口顶部条带内，命中则临时取消穿透。
- 实测：轮询周期 40ms、条带高 48 逻辑像素，正常移动鼠标无可感延迟。

## 六、引擎选型

### 6.1 OCR

| 引擎 | 定位 | 体积 |
| --- | --- | --- |
| **Windows.Media.OCR**（系统内置） | 免下载快启路径，开箱可用 | 零额外体积 |
| PP-OCRv6 small ONNX（RapidOCR 路线） | **默认引擎**：首次启用时按需下载 | 约 +40–70MB |
| 云端 OCR | 可选，用户自带 key | 无 |

> **决策变更（2026-10-26）**：原设计为「系统 OCR 默认、离线包可选」。实测发现中文系统的 Windows OCR 只有 `zh-Hans-CN` 引擎、读英文会吞空格（`The quick brown foxjumps over the lazy dog.`），质量不足以承担默认路径。因此反转为**离线包承担主力识别，系统 OCR 作为零下载的降级/快启路径**。详见 [DECISIONS.md](DECISIONS.md) D7。

体积依据：Umi-OCR v2.1.5 Windows 版 Rapid 98.6MB / Paddle 128.1MB；RapidOCR v3.9.0 的 whl 从 15MB 涨到 29.5MB，因 PP-OCRv6 det_small 9.5MB + rec_small 20MB（官方 release note 转述，2026-06）。

### 6.2 翻译：阿里云机器翻译通用版（BYOK）

| 对比项 | 阿里云机器翻译 通用版 | DeepL API |
| --- | --- | --- |
| 每月免费额度 | **100 万字符**（主账号，子账号共享；每月 1 日刷新，不结转） | 50 万字符（API Free 档） |
| 超额单价 | 后付费 **50 元/百万字符**；1000 万字符资源包 480 元 | Pro 档 **€22.00/百万字符**；另有第三方来源称 $5.49/月 + $25/百万字符 |
| 语种覆盖 | 214 种 | 约 30 种 |
| 注册门槛 | 国内账号 + 实名认证 | API Free 需绑卡，有来源称仅支持境外信用卡 |

来源：阿里云帮助中心《公共云机器翻译通用版的定价方式》（2026-08-27）、DeepL 官方帮助中心《DeepL API 的字符计数与计费》、DeepL 官网 Pro API 页（2026-05）。

⚠️ **数据分歧标注**：DeepL 超额单价存在 €22/百万字符（官方页）与 $25/百万字符（第三方）两种说法，来自不同页面与时点，本文标注分歧不择一。

**选型理由**：免费额度为 DeepL 两倍；€22 明显高于 50 元人民币；国内注册不需境外信用卡（对用户与未来的开源用户都是硬门槛）。

**用量测算**（假设值）：单次约 300 字符、每天 50 次 = 45 万字符/月，在免费额度内，成本为 0。重度使用（每天 100 次 × 500 字符 = 150 万字符/月）超额 50 万字符，约 **25 元/月**。

**BYOK 架构**：每个用户填自己的 AccessKey，消耗自己的额度；开发者零成本、零用量风险。DeepL 保留为可选引擎。

**可选增强引擎**：阿里云 Qwen-MT，官方口径"每百万输出 token 低至 2 元"（来源：百度百科，2025-11，⚠️ 非官方定价页，使用前需去百炼控制台核实实时价格）。

### 6.3 AI 赋能的取舍

| 决定 | 内容 |
| --- | --- |
| ✅ 做 | LLM 作为可选翻译引擎（与阿里云 AccessKey 同一套鉴权，只多一个适配器） |
| ✅ 做 | 术语一致性记忆：历史翻译结果存本地形成个人术语表，命中缓存则复用 |
| ❌ 否决 | AI 生图 / 总结 / 问答——与核心场景无关，加剧界面繁琐，带来成本 |
| ❌ 否决 | 客户端跑本地 LLM——体积与内存爆炸，与轻量定位冲突 |
| ❌ 否决 | 训练或微调自有模型——无语料、无必要 |

### 6.4 Java 与 Python 的定位

- **Java：否决。** 加 Java 需打包 JVM（+40MB 起）或走 GraalVM native-image（配置复杂），直接毁掉 5–15MB 体积目标，且无可替代位置。唯一合理场景是未来做 Android 版，属另一个项目。
- **Python：用，但只在开发期，不进发行版。** ① OCR 引擎评测脚本（批量跑引擎出准确率对比表）；② 背景色算法原型（先验证"边缘像素众数色 + 方差判定降级"再移植 Rust）；③ 离线模型包的下载与 SHA256 校验。

## 七、零服务器架构

不需要服务器，全部落在本机 + GitHub 免费能力：

| 需求 | 方案 |
| --- | --- |
| 配置、历史记录、生词本 | 本地 SQLite，存 `%APPDATA%` |
| 截图缓存 | 本地临时目录，可配置保留天数与自动清理 |
| 翻译 API | 直连服务商，用户自带 key，代码不经任何中转 |
| 离线 OCR 模型包（约 30MB） | GitHub Releases（免费、自带 CDN、单文件上限 2GB） |
| 自动更新 | Tauri updater 插件，同样从 Releases 拉取 |

即：**一个免费 GitHub 仓库 = 代码托管 + 模型分发 + 更新服务器。**

⚠️ 已知问题：GitHub Releases 国内下载速度不稳定（Umi-OCR 文档提到约 20KB/s，故其另设国内网盘镜像）。README 需同时给国内网盘备用链接（M4 处理）。

## 八、组件架构与数据流

```
┌── UI 层（WebView 窗口）
│   ├── 选区遮罩窗    全屏、暗化、拖框，用于新建玻璃窗
│   ├── 玻璃窗        透明、置顶、可穿透，内含「覆盖渲染层」
│   └── 设置窗        引擎、AccessKey、快捷键、主题、专注模式、离线包
│
├── Rust 核心层
│   ├── hotkey        全局快捷键注册与分发
│   ├── capture       屏幕矩形抓取（抓前设 WDA_EXCLUDEFROMCAPTURE，无需隐藏自身）
│   ├── ocr/          引擎 trait + system / onnx / cloud 三实现
│   ├── translate/    引擎 trait + aliyun / qwen-mt / deepl / custom
│   ├── layout        OCR 行框 → 段落聚合 → 回填坐标计算
│   ├── bgcolor       背景色采样、方差判定、降级决策
│   ├── glossary      术语缓存与命中复用
│   └── store         配置与历史持久化
│
└── 资源
    ├── 内置          不含任何 OCR 模型（系统 API）或仅含极简包
    └── 按需下载      PP-OCRv6 small ONNX 离线包
```

**一次完整翻译的数据流**：

```
快捷键 → hotkey 分发
      → capture(玻璃窗矩形，每次现取) → Bitmap
      → ocr.recognize → [{文本, 行框坐标, 置信度}]
      → glossary.lookup → 命中则跳过翻译
      → layout.group_lines → [{段落文本, 合并框, 行框列表}]
      → translate.batch → [译文]
      → bgcolor.sample → [每段背景色 + 是否降级]
      → 前端渲染：背景色块盖原文 + 译文自适应字号回填
      → glossary.store + store.history（专注模式下跳过）
      → 窗口进入「覆盖显示」态
```

**抓屏的关键实现（M0/T4 结论）**：抓屏前对玻璃窗调用 `SetWindowDisplayAffinity(hwnd, WDA_EXCLUDEFROMCAPTURE)`，之后直接 `BitBlt` 目标矩形即可——自己不会入画，**零闪烁、零往返**。"隐藏窗口 → 抓 → 恢复"的做法实测耗时 201ms 且闪一次，已放弃。

⚠️ 注意 `WDA_EXCLUDEFROMCAPTURE` 需要 Windows 10 2004+；更早的系统上它等同 `WDA_MONITOR`，行为不同。官方明确它不是安全/DRM 特性，无法阻止手机拍屏。

## 十、已知风险与限制

| 风险 | 现状 | 应对 |
| --- | --- | --- |
| 抓屏截到自己 | ✅ 已解决 | `WDA_EXCLUDEFROMCAPTURE`，零闪烁（M0/T4） |
| 透明窗口在 WebView2 上失效 | ✅ 未复现 | M0/T1 通过；仍保留为版本相关风险 |
| 多显示器 + 混合 DPI 坐标错位 | ✅ 已摸清 | 全用物理像素；矩形每次现取（M0/T3） |
| 点击穿透后收不到 hover | ✅ 已解决 | Rust 侧 40ms 轮询 `GetCursorPos`（M0/T2） |
| 复杂背景覆盖失效 | 待 M2 | 降级为半透明深色底 + 白字 |
| 全屏 DirectX 游戏抓不到 | 接受 | 需 `Windows.Graphics.Capture`，V1 不做，README 写明 |
| 译文长度不可控 | 待 M2 | 字号自适应 + 下限 + 折行 + 提示 |
